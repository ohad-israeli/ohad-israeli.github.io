## The business problem

Picture the alerting feature almost every data platform ends up building: a
customer defines a rule — flag a login from a new country, tell me when this
metric crosses a threshold, catch any transaction shaped like fraud — and the
platform is supposed to tell them the moment it happens. Security tools do
this. Observability platforms do this. Fraud and risk systems do this. A
common way teams solve it: land the incoming events in an analytical data
store, and re-run every customer's rules against it on a timer — every few
seconds, every minute, whatever the schedule allows.

That's a perfectly reasonable way to start. It's also a design with two
questions built into it that eventually catch up with every system built this
way: **is it scalable, and is it cost-effective?** Scalability breaks down
because detection latency is set by the poll interval, not by when the event
actually happened — a rule can only fire as fast as the next scheduled query
runs, no faster. Cost breaks down because every poll re-scans the same landed
data against the same, growing set of rules — double the customers or double
the rule count, and the query engine is doing double the work on every single
cycle, forever, whether or not anything actually matched.

The system this project is built around is a real version of that pattern: a
platform ingesting a genuinely large, continuous stream of events — the kind
of pipeline where the input stops being worth describing in "events per
second" and starts being worth describing in **gigabytes per second** —
evaluating each customer's own detection rules against it by repeatedly
querying an analytical store. Reasonable place to start; not where it ends up
working at scale, once traffic, customer count, and rule count are all
climbing at the same time.

The fix isn't a bigger analytics cluster running the same queries faster —
it's not querying after the fact at all. **Confluent Platform for Flink**
evaluates every event against a customer's rules **the moment it arrives**,
in-stream, and Confluent Cloud only ever has to size and bill for the
*filtered* output, not the raw firehose. Adding a rule, changing one, or
onboarding a new tenant becomes a message into already-running state, not a
query change and not a redeploy.

## Try it yourself

The [repo](https://github.com/ohad-israeli/flink-rule-router) has the whole
pipeline: the Flink Application job, a listing connector that publishes only
blob *URIs* (never content) so the multi-GB/s firehose never has to land in a
topic, a predicate compiler that turns a SQL-like `WHERE`-clause into the rule
JSON the job consumes, and the Kubernetes/Terraform to deploy it all to a real
Confluent Platform for Flink cluster with Confluent Cloud carrying the
low-rate rule and output topics. Every module builds and runs independently —
see the repo's README for the exact commands.

## The key piece

`flink-app`'s core is a `KeyedBroadcastProcessFunction`, keyed by the event's
`customerId`, holding each customer's compiled rules in RocksDB-backed
broadcast state:

```java
BroadcastStream<RuleUpdate> ruleUpdates = env
    .fromSource(filterControlSource, WatermarkStrategy.noWatermarks(), "filter-control")
    .broadcast(CustomerScopedRuleMatchFunction.RULES_STATE_DESCRIPTOR);

DataStream<Match> matches = events
    .keyBy(RawEvent::getCustomerId)
    .connect(ruleUpdates)
    .process(new CustomerScopedRuleMatchFunction());
```

Keying by `customerId` is what turns "check every event against the *entire*
rule set" into "check every event against *only its own customer's* 3–20
active rules" — regardless of how many other customers' rules are sitting in
the same job's broadcast state. Toggling a rule, editing one, or onboarding a
new customer is just another message on `filter-control`; the broadcast
function's `processBroadcastElement` updates one entry in a
`Map<customerId, List<CompiledRule>>` — no redeploy, no savepoint, no schema
migration.

The other half that makes this viable at the source's actual throughput:
fetching each event's content is a `RichAsyncFunction`
(`AsyncDataStream.unorderedWait`), not a blocking map. A synchronous
fetch-per-record blocks its subtask for the full network round-trip and caps
throughput around 1,200–3,000 events/min per subtask, regardless of how fast
upstream listing runs — nowhere near the volume this needed to clear.

## Running it

```bash
cd flink-app && mvn package                       # -> target/filter-route-job.jar
mvn install -DskipTests                           # required once, for predicate-compiler's cross-validation test
cd ../predicate-compiler && mvn package            # -> target/predicate-compiler.jar

# publish a rule
java -jar target/predicate-compiler.jar \
  --customer-id cust-1 --rule-id rule-1 \
  --bootstrap-servers localhost:9092 --topic filter-control \
  --where "region = 'us-east'"
```

`cmf-deploy/` packages the same jar as a real `FlinkApplication` custom
resource for Confluent Platform for Flink on Kubernetes; `terraform/` and
`terraform-confluent-cloud/` stand up the AKS/CMF cluster and the Confluent
Cloud environment respectively. The repo README has the full path from a
laptop-only test to the real deployment.

## Results

Everything below ran against a real Confluent Platform for Flink deployment
on AKS and a real Confluent Cloud cluster — not a local dev cluster standing
in for both:

- **Load test**: 100,000 events end-to-end at parallelism 1 — one subtask, no
  scale-out — sustained **~105,600 events/min**, comfortably clearing the
  required throughput target with zero loss.
- **Failure recovery**: killed the running TaskManager mid-batch. Kubernetes
  rescheduled it automatically; the job resumed from its last checkpoint with
  **zero data loss** — every in-flight match redelivered exactly once, the
  expected at-least-once behavior of rewinding to a checkpoint, not a bug.
- **Rule scale**: 3,372 rules across 300 customers loaded into one job's
  broadcast state. 30 sampled customers, each matched against exactly their
  own rule — **30/30 correct**, and none of the ~3,072 decoy rules in the same
  state ever fired for the wrong customer.
- **Savepoint upgrade**: triggered a planned upgrade with that same
  3,372-rule state loaded. The new job matched a customer's event correctly
  **without republishing a single rule** — the whole broadcast state survived
  the upgrade intact.

## Why it matters

The pattern here generalizes past this one pipeline: any per-tenant rule or
alert evaluation that's currently implemented as a scheduled query against an
analytical store — a SIEM, an observability platform, a fraud engine, an IoT
alerting system — can move from "detect on the next poll cycle" to "detect
the moment the event arrives," without the query cost of re-scanning growing
history on every cycle. Confluent Platform for Flink's broadcast state does
the part that's usually the hard sell in that move: keeping thousands of
independent, frequently-changing rule sets live in one job, cheaply, without
a redeploy on every change.

Full code, configs, and deployment assets are in the
[repo](https://github.com/ohad-israeli/flink-rule-router).
