## What this repo demonstrates

A self-managed Confluent Platform cluster — Kafka, Kafka Connect, and Schema
Registry, running on its own VM, outside Confluent Cloud entirely — gets
cataloged and governed from Confluent Cloud's console through Confluent's
**Unified Stream Manager (USM)**, connected over real ingress PrivateLink. A
Debezium CDC connector, registered only against the self-managed side,
auto-creates a topic and its schemas the normal way CDC connectors do — no
manual per-table setup. The question this project actually answers: does any
of that show up in Confluent Cloud's catalog on its own, or does someone have
to register it by hand?

## Why this matters

A common hybrid pattern: the source of truth stays on-premises — a core
banking ledger, a hospital's patient records, anything where the raw data
itself isn't allowed to leave a specific network or jurisdiction — while the
business still wants that data working in the cloud. A CDC connector
captures every change on-premises the moment it happens, and those events
get synced into the cloud, where the real downstream work runs: enrichment,
joins with other cloud-native systems, landing in a data lake, feeding the
analytics and ML pipelines that only make sense to run there.

The moment you're operating that way, you've got two separate estates —
on-prem and cloud — each generating its own topics, schemas, and connectors,
and someone has to know what exists on both sides to trust the pipeline
connecting them. That's the specific gap this project checks: once
something is created purely on the on-prem side, with a human never
registering it anywhere, does it actually surface in the cloud's catalog on
its own? USM is built to answer that with one console instead of two — and
it's a genuinely new capability, so this project builds the real thing to
find out whether it delivers.

## How this actually gets published — the mechanism itself

"Unified governance" turns out to be **two completely independent
mechanisms sharing one console**, and neither one is what you'd guess from
the name "USM Agent." Here's what's actually running, confirmed by reading
the real config on the box and the real traffic in its access log — not
from the marketing description.

### Topics and connectors: self-reporting, not discovery

The natural assumption is that some USM component actively scans the
cluster — connects to it, lists its topics and connectors, and reports back.
**That's not what happens.** The "USM Agent" service on the VM is, in its
entirety, a local Envoy proxy — `ps aux` shows its only process is
`envoy -c usm-agent.yaml`. It has no code that inspects Kafka, Connect, or
anything else. It doesn't ask any component for a topic list.

Instead, **every Confluent Platform component already knows what it's
running, and reports that itself** — through `TelemetryReporter`, a plugin
that ships with the platform (not something USM adds), pointed at a new
local destination:

```properties
# Kafka Connect's connect-distributed.properties (broker/controller carry the
# equivalent confluent.telemetry.exporter._usm.* block):
metric.reporters=io.confluent.telemetry.reporter.TelemetryReporter
confluent.telemetry.exporter._usm.enabled=True
confluent.telemetry.exporter._usm.type=http
confluent.telemetry.exporter._usm.client.base.url=http://cp-node:10000
```

Every broker, the controller, and the Connect worker each push their own
metrics and events to `http://cp-node:10000` — the local Agent's dataplane
port — on their own schedule. The Agent's *entire* job on receipt is:
inject Confluent Cloud credentials and the environment-id header, and relay
the request over the network. That's confirmed directly by its route table
(`usm-agent.yaml`), which does nothing but forward two paths to two
different Confluent Cloud backends:

```yaml
routes:
  - match: {prefix: "/v1/events"}    # -> Metadata Receiver (topics/connectors/configs)
    route: {cluster: ccloud, prefix_rewrite: "/mr/v1/events"}
  - match: {prefix: "/v1/metrics"}   # -> Telemetry Receiver (throughput/rate time series)
    route: {cluster: ccloud, prefix_rewrite: "/tr/v1/metrics"}
```

The real access log shows exactly this split in practice — `kafka.server`
and `kafka.connect`-tagged POSTs hit `/v1/events` (this is where the topic
list, the connector list, and configs travel — the controller's config
explicitly names the route `catalog-events`), while a wider set of
component tags (`kafka.server`, `kafka.connect`, `kafka.consumer`,
`kafka.producer`, `kafka.rest`, `kafka.admin.client`) hit `/v1/metrics` for
the throughput/rate numbers the Console's topic table shows.

So: **discovery isn't the Agent's responsibility at all — it doesn't have
one.** It's each component's own, already-existing self-reporting,
redirected to a local relay instead of wherever it went before. That also
explains why an absent Agent produces total silence rather than an error:
the components keep trying to push to `cp-node:10000` on schedule
regardless of whether anything's listening there. Nothing is ever "asking"
the Agent to go find something, so there's nothing to fail loudly when it can't.

### Schemas: a completely different mechanism, bypassing the Agent entirely

Schema forwarding doesn't go through the Agent, the Envoy proxy, or port
`10000` at all. The self-managed Schema Registry has its own extension
(`io.confluent.schema.registry.usm.UsmSchemaRegistryExtension`) with its own
direct API key/secret and its own endpoint URL, configured independently of
anything USM-Agent-related:

```properties
# schema-registry.properties
schema.registry.resource.extension.class=io.confluent.schema.registry.usm.UsmSchemaRegistryExtension
usm.schema.registry.remote.endpoint=https://psrc-xxxx.eastus.azure.confluent.cloud
usm.schema.registry.remote.api.key=...
usm.schema.registry.remote.api.secret=...
```

Once its global mode is flipped to `FORWARD`, every new schema write is
synchronously redirected straight to Confluent Cloud's Schema Registry, over
its own connection, the moment it happens locally:

```bash
curl -X PUT -H 'Content-Type: application/vnd.schemaregistry.v1+json' \
  --data '{"mode":"FORWARD"}' 'http://localhost:8081/mode/:.__GLOBAL:'
```

That specific path (`/mode/:.__GLOBAL:`) is the non-obvious part — the more
guessable `/mode` or `/mode/__GLOBAL` both fail silently against the wrong
scope. Configuring the extension (an Ansible variable handles that part) and
*activating* FORWARD mode are two separate steps — miss the mode flip and
every schema write still succeeds locally; it just never reaches the
catalog, with no error pointing at why.

**So, directly**: topics and connectors reach the catalog via each
component's own built-in telemetry self-reporting, relayed (not discovered)
by the Agent; schemas reach it via a synchronous write-proxy on the Schema
Registry that has nothing to do with the Agent. Two different mechanisms,
two different failure modes, and neither one is "the Agent goes and finds
things" — which is the part that doesn't come across from how USM is
described.

## Half the picture, on purpose

This repo only builds the on-premises half — Kafka, Kafka Connect, Schema
Registry, and the USM Agent, all on one self-managed VM — plus the minimum
Confluent Cloud scaffolding needed to register it (an environment, Stream
Governance, the PrivateLink chain). There's no cloud-side pipeline doing any
of the real work. That's deliberate: it isolates exactly one question —
once something exists purely on the on-prem side, created by a connector
that has zero awareness USM even exists, does it show up in Confluent
Cloud's console anyway, or does a human have to register it there by hand?

What actually happened: a real Debezium SQL Server connector, registered
against the **local** Connect worker and Schema Registry only — never
pointed at Confluent Cloud directly, since a connector talking straight to
the cloud registry would obviously show up there and prove nothing about
USM. With Schema Registry's `FORWARD` mode active, its auto-created schemas
appeared in Confluent Cloud's real Schema Registry with no manual step:

```
$ curl -u $SR_KEY:$SR_SECRET $CC_SR_URL/subjects
["sqlserver_source.SourceDB.dbo.TBL_AG_TEST4-value","sqlserver_source-key",
 "sqlserver_source.SourceDB.dbo.TBL_AG_TEST4-key","sqlserver_source-value"]
```

A standalone test schema forwarded in well under 10 seconds from the moment
it was written locally — a synchronous proxy, not a batched or polling
sync.

And what actually shows up in the Console, once the USM Agent is running
and correctly registered: every topic on the self-managed cluster,
including the CDC connector's own auto-created topic
(`sqlserver_source.SourceDB.dbo.TBL_AG_TEST4`), its default topic
(`sqlserver_source`), the Debezium schema-history topic
(`schema-changes.sourcedb`), and Kafka Connect's own internal topics
(`connect-cluster-configs`/`-offsets`/`-status`) — all with zero manual
registration:

So: yes — a CDC connector creating a topic dynamically, with zero awareness
that USM exists, is enough for that topic to reach Confluent Cloud's catalog
on its own.

One real, undocumented dependency surfaced while setting this up: Confluent
Cloud's Schema Registry cluster only provisions once the *first* Kafka
cluster exists in an environment — not when the Stream Governance package is
set, and not by USM Agent registration. A project with zero Confluent
Cloud-native Kafka clusters (the point of this one) needs one minimal,
unused cluster purely to trigger that provisioning.
