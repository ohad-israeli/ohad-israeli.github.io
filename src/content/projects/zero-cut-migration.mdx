## The business need

Picture a company whose event backbone runs on self-managed Kafka. It wants to move to **Confluent Cloud** to stop operating brokers, scale elastically, and get managed Schema Registry and governance. Two constraints make that hard:

- **Dozens of producers and consumers**, owned by different teams, with no maintenance window in which all of them can restart against a new address.
- A security rule that the new cluster has **no public Kafka endpoint**. It must be reachable only over private networking inside the company's own VPC.

The migration therefore has to be *zero-cut*. Clients keep their existing connection, the data arrives with consumer positions intact, and the switch happens underneath them in one operator action.

## Who this helps

- **Platform and infrastructure leads** planning a Kafka move who can't coordinate every team on one date.
- **Security and network teams** that require private connectivity to managed services.
- **Application teams** who want the migration to be someone else's problem.
- **Architects** weighing a flag-day cutover against a gradual one.

## The approach

Clients connect to a **CPC Gateway** instead of to a broker. A **source-initiated Cluster Link** replicates topics and consumer offsets to a private Confluent Cloud Dedicated cluster. It dials **outbound** over **GCP Private Service Connect**, the direction private networking allows. When lag reaches zero, **[KCP](https://github.com/confluentinc/kcp)** fences the Gateway briefly, promotes the mirror topics, and re-points the Gateway at Confluent Cloud. Clients reconnect to the same address.

Getting clients onto the Gateway is a calm prerequisite, done while the Gateway still routes straight to the source, so behavior is identical. Each team repoints on its own schedule. Handing clients a DNS name you control instead of a broker address makes even that step a single record change.

## The challenge, and what we discovered

The catch is **DNS**. A private Confluent Cloud cluster publishes its broker addresses in public DNS, and those are Confluent's internal private IPs, which your VPC can't route to:

```text
$ getent hosts lkc-xxxxxxx.<domain>.us-east1.gcp.confluent.cloud
10.1.32.2   lkc-xxxxxxx...     # published broker IP, unreachable from your VPC
```

A client resolves the bootstrap name to an address it can never reach, and the answer looks perfectly valid. The fix is a **private Cloud DNS zone** for the cluster's domain, with a wildcard record pointing at your **Private Service Connect endpoint IPs**. With that override in place, the bootstrap name and every broker hostname resolve to the endpoints. The source-initiated link then came up `ACTIVE` on both sides, and the mirror drained to zero lag with 190 messages replicated.

In a separate run, the cutover sequence (drain lag, fence, promote topics, switch the Gateway upstream) completed end to end, and the topic became a normal writable topic on Confluent Cloud.

## Summary

- **Clients address the Gateway, not a broker**, so only the Gateway's upstream changes at cutover.
- **Source-initiated Cluster Linking** moves data and offsets in the one direction private networking permits.
- **Private DNS is the step that gets missed.** Override resolution to your PSC endpoints and the rest follows.
