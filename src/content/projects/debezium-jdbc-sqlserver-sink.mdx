## The business need

Picture a company whose core transactional system runs on an on-premises SQL Server. The business wants that data in the cloud, **continuously**, for three reasons:

- **Analytics and reporting** that run on fresh data, not last night's batch.
- A **phased migration** to the cloud, with old and new running side by side.
- A **warm disaster-recovery replica** that is ready when it's needed.

The requirements are firm. The copy must stay current in near real time, add **no downtime or load to production**, and match the source **exactly**, down to the `IDENTITY` primary keys that downstream systems rely on.

## Who this helps

- Teams planning a **SQL Server to cloud migration** that can't afford a cutover weekend.
- **Data and analytics owners** who need a trustworthy, current copy outside production.
- **Resilience and DR leads** who want a warm replica without bespoke scripts.
- **Platform engineers** who would rather run configuration than maintain a custom sync tool.

## The approach

SQL Server's built-in Change Data Capture records each change as it happens, so nothing has to poll your production tables. **Debezium** publishes those changes to **Confluent Cloud** (managed Kafka and Schema Registry), and the **Debezium JDBC sink** writes them into **Amazon RDS for SQL Server**. It's all configuration, with no pipeline code.

## Things to pay attention to

Replicating rows is the easy part. Replicating **identity keys** is where it quietly goes wrong. SQL Server normally generates identity values itself, so a standard sink re-numbers every row and source and target IDs drift apart without any error. For a system whose downstream consumers join on those IDs, that is silent data corruption. Two settings on the sink prevent it:

1. **`dialect.sqlserver.identity.insert=true`.** Its role is to insert the source's identity values verbatim instead of letting SQL Server generate new ones. It needs Debezium JDBC connector version 3.0.7 or newer.
2. **`replication=true` on the sink's connection URL.** When the key is declared `NOT FOR REPLICATION`, SQL Server honors an explicit identity value only on a connection that identifies itself as a replication connection. Its role is to make that so. Without it, SQL Server silently ignores the value you send.

To check, we seeded the source with deliberately non-contiguous keys (`1, 11, 21, 31, 41`). They landed in the target unchanged.

## Summary

- **Continuous, exact replication** from on-prem SQL Server to the cloud is achievable with off-the-shelf Debezium connectors and Confluent Cloud.
- **Identity keys** used to force a custom sink. Now they take one dialect flag and one connection-string setting.
- The same stream can feed analytics, a migration, and a DR replica without touching production.

Full configuration, SQL, and run instructions are in the [repo](https://github.com/ohad-israeli/debezium-jdbc-sqlserver-sink).
