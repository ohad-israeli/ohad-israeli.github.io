## What this repo demonstrates

A Flink SQL job — an enrichment join between a clickstream and a customer
table — submitted with **no custom JAR**, running against a **real Confluent
Platform backend** (Kafka, Schema Registry, Control Center, all deployed via
Confluent for Kubernetes), with the whole thing managed through **Confluent
Manager for Apache Flink (CMF)**. Everything — CMF, the Flink Kubernetes
Operator, and Confluent Platform itself — runs on a single Kubernetes
cluster on one existing box. No new cloud infrastructure, no separate bill.

## Why this matters

A common way teams evaluate stream processing is standing up open-source
Apache Flink themselves — and discovering that "run a Flink cluster" is
really "run a distributed system": high availability, upgrades, security,
and resource isolation across every job anyone submits, all now the team's
own responsibility. Confluent's pitch for Flink managed through CMF is
specifically about removing that layer, and it's worth stating its actual
claims plainly rather than vaguely: one-click integration between Kafka and
Flink with schemas managed automatically through Schema Registry; a
SQL-first developer experience (ANSI SQL, Python, Java, a browser workspace,
a CLI, a VS Code extension); integrated security and access control shared
with the rest of Confluent Platform; one CMF control plane that can manage
Flink workloads across multiple Kubernetes clusters and regions; and
enterprise support behind all of it. (Confluent's latest platform release
also ships an MCP server for Flink — letting an AI agent manage jobs through
natural language — which this project doesn't touch, but is worth knowing
the platform now supports.)

This project checks a specific, testable version of that pitch: can a real
enrichment job be written, deployed, and observed **entirely through SQL and
a managed console**, without anyone hand-operating a Flink cluster or
writing a line of Java?

## The key idea: a CMF Statement, not a job

CMF doesn't have a separate "streaming job" object. Everything — a one-shot
`CREATE TABLE`, a seed `INSERT`, and a long-running enrichment — is the same
kind of resource: a **Statement**. Here's the actual detail view for the
one that's still running:

<figure>
  <img
    src="/screenshots/managed-flink-sql-demo/cmf-statement-detail-enrichment.png"
    alt="CMF's detail view for the customer-click-enrichment statement: status RUNNING, Flink version v1_19, Kind INSERT_INTO, Bounded false, Append only true, Parallelism 1, JobManager 1x (0.5 CPU / 1 GiB), TaskManager 1x (1 CPU / 1 GiB), and the full SQL text: INSERT INTO customer_click_activity SELECT c.click_id, c.user_id, cu.customer_name, cu.customer_email, c.url, c.user_agent, c.view_time FROM clicks JOIN customers."
  />
  <figcaption>The running statement's own detail page in CMF.</figcaption>
</figure>

A few fields here are worth actually reading, not skimming past:

- **Kind: `INSERT_INTO`** — even a continuously-running enrichment job is,
  to CMF, just an `INSERT` statement. There's no separate "streaming
  application" resource type to learn; the same `flink statement create`
  command that runs a one-shot `CREATE TABLE` also runs this.
- **Bounded: `false`** — this is what actually marks it as an unbounded,
  continuously-running query rather than a batch job that finishes. CMF
  infers this from the query itself; nobody flags it explicitly.
- **Append only: `true`** — the sink only ever appends rows, never retracts
  one. That's a direct, checkable consequence of this being a plain,
  non-temporal stream-stream join with no aggregation — the kind of detail
  that would flip to `false` the moment the query changed shape.
- **Parallelism: 1**, one JobManager (0.5 CPU / 1 GiB), one TaskManager
  (1 CPU / 1 GiB) — sized for a single lightweight demo statement, not
  tuned for real throughput. Scaling this is a compute-pool setting, not a
  code change.

And the SQL itself is right there in the console — the exact statement
that's running, not a paraphrase of it. Nothing about submitting this
needed a JAR, a Dockerfile, or a JobManager REST call.

## Try it yourself

The [repo](https://github.com/ohad-israeli/managed-flink-sql-demo) has the
whole thing: the CFK manifests for a real Confluent Platform deployment, the
CMF/Operator install, all six SQL statements as separate ordered files
(`sql/01_create_clicks.sql` through `sql/06_customer_click_enrichment.sql`),
and `scripts/demo.sh start|stop` — a single script that brings the whole
stack up (or pauses it) on demand, including the port-forwards, tested
through a full cold restart with the enrichment job resuming correctly on
its own. See the repo's README for the exact commands.

Full manifests, SQL, and scripts are in the
[repo](https://github.com/ohad-israeli/managed-flink-sql-demo).
