## The business need

Picture a company whose orders stream through Kafka. Analysts and BI tools need to query that data with plain SQL, so the data team builds a pipeline whose only job is copying it somewhere queryable: a scheduled Spark or Airflow job reads the topic, writes Parquet or Iceberg files to object storage, and updates a catalog.

That pipeline needs its own compute, its own monitoring and its own on-call rotation for when it falls behind or breaks. And the data is only as fresh as its schedule allows. It is a second system to run, whose entire purpose is to keep a copy in sync.

## Who this helps

- **Data and analytics leads** who want fresh streaming data in the lakehouse without another pipeline to own.
- **Platform teams** retiring Spark and Airflow jobs that exist only to move data.
- **BI and analytics users** who want to query streaming data with the engine they already use.
- **Architects** who want an open table format and no vendor-only export.

## The approach

**Confluent Tableflow** removes the pipeline instead of optimizing it. You attach Tableflow to a topic, and Confluent keeps an **Iceberg table** in sync with it. Any Iceberg-aware engine (DuckDB, Snowflake, Athena, Trino, Spark) reads it through a standard REST catalog endpoint.

In Terraform, the whole "pipeline" is one resource on the topic, with Confluent-managed storage and the Iceberg format:

```hcl
resource "confluent_tableflow_topic" "orders" {
  display_name  = confluent_kafka_topic.orders.topic_name
  managed_storage {}
  table_formats = ["ICEBERG"]
  # environment, cluster and credentials omitted
}
```

## Things to pay attention to

**1. The default is to suspend on failure.** Tableflow's error handling defaults to `SUSPEND`: a record that can't be materialized pauses the whole table instead of being skipped. That's a sensible default, since silently corrupting a table is worse than stopping, and it's [documented](https://docs.confluent.io/cloud/current/topics/tableflow/operate/configure-tableflow.html), along with the `skip` and `log` modes. We saw it when we added a field with a default to the Avro schema, a backward-compatible change: the connector kept running, but the table paused. Choose the error-handling mode deliberately before a schema changes in production. We did not test whether `log` would have kept the table running.

**2. Managed storage versus your own bucket.** We used Confluent-managed storage, so there was no S3 or ADLS bucket to provision. If you need your own bucket and an external catalog such as AWS Glue, Snowflake Open Catalog or Unity Catalog, that is a separate setup with your own cloud account and IAM.

## Summary

- **The topic becomes the table.** No copy job, no schedule, no staleness window from a batch.
- **It stays open.** The result is a real Iceberg table, readable by any engine that speaks the REST catalog protocol.
- **Decide on failure handling before the schema changes.**
- **What we ran:** a Datagen producer feeding an `orders` topic, Tableflow enabled with managed storage, and a DuckDB query over the REST catalog that returned readable order rows.

Terraform and the query script are in the [repo](https://github.com/ohad-israeli/zero-etl-lakehouse).
